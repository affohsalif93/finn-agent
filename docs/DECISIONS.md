# Decision log

Decisions made while scoping the case study, with the reasoning. Source material for the German note ("was ich an der Vorgabe geändert habe und warum").

| # | Decision | Reasoning | Alternatives considered |
|---|---|---|---|
| D1 | **The LLM never calculates.** It extracts, classifies and writes; code computes every number. | Explicit rule in the brief; numbers must be reproducible and auditable. | – |
| D2 | **Extract contracts once into reviewed profiles** (JSON), reuse them for every mail. Re-extract only on file-hash or schema change. | The interpretation is written down once, reviewed by a person and frozen. Avoids reading contracts differently per run (e.g. 3.37 vs. 3.57). Fast and reliable in the live demo. | Send the full contract text on every request: works technically, but every run reinterprets and nothing can be reviewed. |
| D3 | **No RAG.** The whole contract goes into the extraction call. | 13 pages ≈ 10k tokens fit easily into context. Covenants span clauses (§ 13 → § 1 → Anlage 3); chunk retrieval breaks those cross-references and can miss definitions silently. | RAG: useful later for cross-contract Q&A over many documents (roadmap). |
| D4 | **Keep the full text next to the profile.** Profiles store verbatim quotes + pages; a second LLM pass (full text + profile) checks for omissions; a deterministic keyword scan must account for every covenant signal word. | Answers the concern that extraction loses nuance. Every parameter links back to its source text. | Profile only: risk of silently lost details. |
| D5 | **Covenants as recipes over building blocks + an escape hatch.** Defined terms (EBITDA, Finanzverbindlichkeiten, Schuldendienst) live per contract as named definitions; covenants reference them. Each covenant states which plan building blocks enter numerator / denominator, with weights (e.g. 0.5 × Sonderposten) and whitelisted conditions (e.g. shareholder loan excluded if qualified subordination). The metric type (equity ratio, net debt / EBITDA, DSCR) stays as a label and for type-specific extras. Anything not expressible goes into `unmapped_components` → no calculation, manual review. | The ratio shape is standard; the contract wording decides what goes in. That difference *is* the test (3.37 vs. 3.57). Recipes handle new contracts without new code, generate the formula shown in the mail, and tell the plan reader which blocks it must find. | Fixed per-type parameters (first draft): a new variation needs new code. LLM writes the formula freely / formula strings: not auditable, needs a parser. |
| D6 | **Plan read by labels, not fixed cells.** Contract-neutral list of ~20 building blocks (plus plan facts) found by row label + column header; every value keeps its cell reference. If items are missing: LLM mapping fallback on a **labels-only skeleton** (no values), verified by accounting tie-outs before use. | Other utilities use other templates; rows and sheets move. The LLM only says *where* a value is; code reads it and the checks catch wrong mappings. In the product: the mapping is confirmed once per customer (plan profile). | Hard-coded cells: breaks on any template change. Sending the whole sheet to the LLM: exposes the figures and lets the LLM touch numbers. |
| D7 | **Fail closed on input.** Checks with BLOCK / WARN / INFO severity (company, plan year, units, balance sheet balances, tie-outs, loans vs. contracts). Never confirm compliance when a blocking check fails. | A wrong "alles eingehalten" sent to a bank is worse than no answer. | Best-effort processing. |
| D8 | **Recompute from scratch on every run.** The mail thread is only used to assemble the input (request + latest valid plan), never to carry numbers. | Deterministic results; revised plans and new threads need no conversation memory. | LLM keeps context across messages: numbers can leak between versions. |
| D9 | **Temporal for orchestration**, core logic framework-independent, plus a direct `.eml` runner. | Durable steps (resume after crash), per-step retry policies, workflow ID = Message-ID (dedup), waiting for follow-up mails (signals), durable timers for future reminders, Web UI as operator console. The direct runner keeps tests simple and is a safety net in the demo. | Plain Python + own checkpointing; n8n (calculation would live in code nodes, hard to test/version); LangGraph (our flow is a fixed pipeline, not an improvising agent). |
| D10 | **IMAP polling, no inbound webhook / API for the case.** | Only outbound connections: no public URL, domain or open port; runs on a laptop or any VM. Delay of seconds is irrelevant for the demo. | Webhook via mail service + FastAPI endpoint: the product option; the workflow stays the same, only the starter changes. |
| D11 | **Mail access behind a connector interface** (fetch new, send reply). Case: IMAP/SMTP on a new dedicated mailbox. | In production Finn gets a mailbox in the customer's own domain (e.g. M365 via Microsoft Graph). Swapping connectors does not touch the workflow. | Vendor-domain address: fine for trials, but confidential data leaves the customer. |
| D12 | **Access control via tenant, not keys in mails.** Case: `ALLOWED_SENDERS` allowlist, open in demo mode (the brief requires accepting unknown senders). Rejections are logged as security events; their attachments are never parsed. | Keys in emails leak. In the product: licence status, verified domains (DNS TXT), users with roles. | Product key in subject/body. |
| D13 | **Observability in three layers:** Temporal Web UI (workflow), Langfuse (LLM calls; trace ID = workflow ID, session = mail thread), run folder (audit trail). Langfuse optional via config. | Debugging, cost tracking and "why did we report 3.37?" traceability. Langfuse is open source and self-hostable (data ownership). | LangSmith: closed source, tied to LangChain. |
| D14 | **Calculation path in the mail itself** instead of a clickable "Rechenweg" as in the demo. | The brief asks for no UI; the mail must be self-contained and auditable. | Links to a web view (needs a UI). |
| D15 | **Plan results worded as early warning**, plus notes the brief does not demand but a finance reader expects: tight-headroom flag, rounding-aware EBITDA/equity sensitivity, V4 margin step, Sparkasse "no covenants" with reason. | All contracts say a plan shortfall is not a default. Cheap to compute, high value. | Plain pass/fail table. |
| D16 | **Resilience over features** (as the brief recommends): retries with backoff, template reply if the LLM is unavailable, idempotent send, partial results when one covenant can't be computed. Provider failover documented, not built. | Numbers never depend on the LLM at runtime (profiles are frozen), so Finn can still answer correctly without it. | – |
| D17 | **Languages:** README, note and Finn's mails in German; internal docs in English. | Reviewers are German; docs are working material. | – |
| D18 | **Every commit is confirmed by the user.** | Deliberate, clean history is part of the submission. | – |
| D19 | **Build our own mail connectors** (IMAP/SMTP now; Graph and Gmail via official SDKs later) behind one interface, with seven robustness rules (ARCHITECTURE §6.1). | Finn needs "new mail in INBOX → reply in thread" at low volume; Temporal already provides retries and queueing. A unified mail service mainly solves full real-time sync of thousands of mailboxes, which we don't need. | Nylas (SaaS, customer mail leaves us), EmailEngine (self-hosted but commercial, stops without a licence), open source (nothing maintained that covers Graph + Gmail + IMAP). Revisit at hundreds of mailboxes or real-time needs. |
| D20 | **Poller is a plain stateless loop outside Temporal; the gate runs in it.** Temporal starts at the first workflow step (`parse_message`). | The poll loop has no state (the inbox is the state), nothing to wait for and no steps to resume; its retry is the next cycle. A scheduled poll workflow would add ~1,400 runs per mailbox per day to the history. Unauthorised mail never creates workflow data. | Temporal Schedule / long-running poll workflow; separate gate API service. |
| D21 | **Data minimisation instead of an anonymisation engine.** Plan **values** never go to the LLM (labels only, in the mapping fallback, D6); the reply LLM writes around placeholders filled by code; the thread is pseudonymised (emails, phones, IBANs, sender name; quotes and signatures stripped) before the intent call; signatory names are masked before contract extraction. The mapping stays local; Langfuse sees the pseudonymised prompts only. | The sensitive data is mostly confidential business data (plan figures, loan terms), and code already keeps it away from the LLM. Each LLM call gets only what its task needs. | NER anonymisation (e.g. Presidio): false positives ("Sparkasse", "Wirtschaftsplan") hurt accuracy, and extraction needs the real contract text anyway. Roadmap option for free-text mails. |
| D22 | **We don't audit the workbook.** Level 1: covenant ratios computed by us. Level 2: figures we use are checked for consistency (leaf values recomputed into totals, compared with the workbook's totals). Level 3: everything else is not checked. | The brief asks for covenant calculation, not a plan audit (prior-year plausibility is explicitly out of scope). Level 2 is needed anyway: `openpyxl` can't evaluate formulas, and cached values may be stale. | Evaluate all workbook formulas (`formulas`, `pycel`): effort without value for the task. |
| D23 | **Own small evaluator on stdlib `decimal`; no formula parser, no unit library.** Recipes are structured data, evaluated by ~100 lines of pure, fully tested code (weighted sums, one division, contract rounding, comparison). | Exact decimals and `ROUND_HALF_UP` are built in. No formula strings means nothing to parse, inject or misparse. Small enough to test exhaustively. | `sympy` / `numexpr` / formula strings; `pint` (one money unit after normalisation is enough); money libraries (EUR only); `babel` (a tested 10-line German formatter avoids locale issues in Docker). |
| D24 | **Units normalised per sheet to T€ when reading.** Unit detected per sheet; unclear → BLOCK; scale checked against contract amounts; percent vs. ratio vs. amount typed in the profile; headroom in pp for percentages; German number parsing/formatting in one place; floats converted via `Decimal(str(x))`. | Ratios are unit-free only if numerator and denominator share a unit; the risk is mixing units, not the unit itself. One internal unit keeps the engine simple. | Units per value through the whole engine (unit library): more complexity for no gain. |
| D25 | **Python 3.12.** | Best libraries for the core of this task: `openpyxl` (cell-level Excel access), `pdfplumber` (page text), stdlib `decimal` (exact arithmetic + `ROUND_HALF_UP`); mature Temporal, OpenAI and Langfuse SDKs; the usual language for AI/automation in finance; no switching cost before the deadline. | TypeScript: strongest Temporal SDK and good mail libraries, but floats by default, weaker PDF text extraction, partly commercial Excel tooling. Fits a later web UI, which can talk to the Python core via an API. |
| D26 | **Small dependency set, managed services where cheap.** Gmail (IMAP/SMTP + app password) as the mailbox, Langfuse Cloud EU (free tier, optional), Temporal dev server in Docker, GitHub Actions CI (ruff, mypy strict on core modules, pytest). Versions locked in `uv.lock`. | Fewer moving parts to break in a live demo; every dependency has a clear job. Gmail delivers reliably; Outlook.com no longer allows IMAP with a password. Self-hosted Langfuse v3 needs Postgres + ClickHouse + Redis + S3, too heavy for the case. | mailbox.org / GMX; self-hosted Langfuse; no CI; no type checks. |
| D27 | **Layered `src/finn/` with one shared `pipeline.py`; contract onboarding as a CLI command.** Core logic (plan, calc, contracts) is pure; adapters (mail, LLM) do I/O; the direct runner and the Temporal activities call the same pipeline functions. Onboarding: `finn contracts extract/check` + git-diff review → committed profiles; hand-written gold profiles in `tests/fixtures/` for the eval. | Core testable without Temporal, mail or LLM; Temporal adds durability, not logic. Contracts don't change during the demo and need human review, so no service is needed and no demo number depends on the LLM. | Onboarding as a service / workflow (product: yes, with an approval signal from the review UI); logic inside activities (untestable without Temporal). |
| D28 | **Contract profile schema v2, derived from all four contracts.** Per contract: verbatim `sources` referenced by ID; `definitions` with `exclusions` / `clarifications`; contract-defined `conditions` with criteria; per-component `if_missing` and `loan_filters`; `loans` with loan-number matching, tranches and repayment schedules; typed `plan_check`, `breach_consequence`, `cure`, `pricing_grid`; contract `examples` as self-tests; categorised `dismissed_mentions`; `label_hints`; `review` / `extraction` metadata instead of an LLM confidence. | Each key exists because a contract needs it: V2/V4 state exclusions that are the traps; V4's subordination test has two criteria while V3 includes shareholder loans regardless; V3/V4 list debt types the plan doesn't show; V3 excludes special / refinancing repayments; the Sparkasse is both V1 lender and V4 syndicate member; plan-check obligations differ (V2 needs an approved plan); V3 prints a sample calculation (1.54) that tests the extraction. Answer key unchanged. | v1 (global sub-recipes, loose source strings, free-text test date, `confidence`): could not express these differences or check them. |
